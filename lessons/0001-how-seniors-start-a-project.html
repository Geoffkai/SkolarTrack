How Senior Engineers Start a Project

The exact mental model and order of operations they use — and why beginners do it backwards.

1 The Mistake Beginners Always Make

When most beginners get a project spec, they immediately open their code editor and ask: "What should I build first?" Then they start with whatever feels most visible — usually a login page, or the homepage UI.

The trap Building UI before your backend works means you're building on nothing. You'll spend hours on a beautiful login form that has nowhere to send the data. Then you'll have to throw it away and rebuild it once the API exists.

Senior engineers invert this. They ask: "What does everything else depend on?" Then they build that first. For SkolarTrack, that ordering looks like this:

1
Database schema Lock the tables before writing any code. Everything — your API, your auth, your frontend — depends on the shape of the data.
2
Project skeleton + environment Folder structure, package.json, .env — the scaffold that holds everything. Do this once, right.
3
Server + DB connection GET /health returns { status: "ok" } and you can query the database. Proof the wiring works before you build anything on top of it.
4
Auth (register + login) JWT auth first, because every protected route depends on it. Don't build scholarships CRUD before you know who's asking.
5
Backend features (API routes) Scholarships CRUD, Applications CRUD — all tested with Thunder Client. Backend is complete and proven before React exists.
6
React frontend Now build the UI. You're not guessing what the API looks like — you know, because you built it. Every API call is a known quantity.
7
Deploy Railway (backend) → Vercel (frontend). Deploy early, deploy often. Don't make "deploy" a scary final boss.
The principle Build from the foundation up. Data layer → server layer → API layer → client layer. Each layer has a stable foundation underneath it before you start.

2 The Day 1 Checklist (Your Actual First Day)

Here's what a senior engineer does on Day 1 of a project like SkolarTrack — not Day 7, not Day 3. Day 1.

# Day 1 goal: server running, database connected, /health responds

1. Confirm your schema is locked (it is — scholarship-tracker-ph.md has it)
2. Create the Neon.tech database and get the DATABASE_URL
3. Set up the project folder structure:
   SkolarTrack/
     server/
       index.js
       src/
         app.js
         routes/
         controllers/
         models/
         middleware/
     client/   ← leave empty for now
4. npm init in server/, install: express pg dotenv
5. Write index.js (calls app.listen only)
6. Write app.js (Express setup, mounts routes)
7. Connect to Neon.tech in app.js using pg
8. Create GET /health route — returns { status: "ok", db: "connected" }
9. Run the server. Hit /health in Thunder Client.
10. If it responds — Day 1 is done. Commit.

That's it. No login page. No React. No scholarships. Just a server that talks to a database. That single working foundation is worth more than a half-built feature.

Why commit at the end of Day 1? Git is your undo button. Senior engineers commit whenever they reach a working state — not when a feature is "done." Day 1 working state = server + DB connection. Commit it with a clear message: feat: Express server + Neon.tech connection, /health endpoint

3 Schema First — Always

Your project doc already has the schema. This is rare and valuable. Most junior devs start coding and discover their schema was wrong on Day 8. You've already done the design thinking. Don't skip it — run it.

Before writing a single route, create your tables on Neon.tech. Open the Neon SQL editor and paste:

CREATE TABLE users (
  id            SERIAL PRIMARY KEY,
  email         VARCHAR UNIQUE NOT NULL,
  password_hash VARCHAR NOT NULL,
  role          VARCHAR CHECK (role IN ('admin', 'student')),
  name          VARCHAR,
  course        VARCHAR,
  school        VARCHAR,
  created_at    TIMESTAMP DEFAULT NOW()
);

CREATE TABLE scholarships (
  id            SERIAL PRIMARY KEY,
  posted_by     INTEGER REFERENCES users(id),
  title         VARCHAR NOT NULL,
  organization  VARCHAR NOT NULL,
  description   TEXT,
  amount        NUMERIC,
  slots         INTEGER,
  requirements  TEXT,
  deadline      DATE NOT NULL,
  status        VARCHAR CHECK (status IN ('open', 'closed')) DEFAULT 'open',
  created_at    TIMESTAMP DEFAULT NOW()
);

CREATE TABLE applications (
  id             SERIAL PRIMARY KEY,
  student_id     INTEGER REFERENCES users(id),
  scholarship_id INTEGER REFERENCES scholarships(id),
  status         VARCHAR CHECK (status IN ('interested','applied','interview','result')),
  notes          TEXT,
  updated_at     TIMESTAMP DEFAULT NOW()
);

Once the tables exist, your models have something to query. Order matters.

4 The Senior vs Junior Comparison

Junior approach
  • Opens VS Code, starts with the login page UI
  • Hardcodes fake data to make it "look real"
  • Builds the full UI, then tries to wire the backend
  • Realizes the schema doesn't match the UI
  • Rewrites half the frontend and half the backend
  • Gives up or ships something broken
Senior approach
  • Reads the spec, locks the schema first
  • Builds the server skeleton — no UI yet
  • Tests every API route with Thunder Client
  • Backend is proven before React is touched
  • Frontend just calls known, working endpoints
  • Ships something that actually works end-to-end

5 Your Architecture is Already Decided — Follow It

CLAUDE.md has your architecture locked in. A senior engineer would recognize this as a gift. You don't have to decide structure on the fly. Every file has a job:

server/index.js       → ONLY: app.listen(PORT)
server/src/app.js     → Express setup, middleware, mount routes
server/src/routes/    → Maps HTTP verb + path to a controller function
server/src/controllers/ → Reads req, calls model, sends res
server/src/models/    → ALL SQL queries. Nothing else.
server/src/middleware/ → auth.js (verify JWT), roles.js (check role)
The rule that keeps code clean Never write SQL in a controller. Never write req/res logic in a model. If you find yourself doing either, stop — you're in the wrong file. This separation is what makes bugs easy to find and code easy to change later.
